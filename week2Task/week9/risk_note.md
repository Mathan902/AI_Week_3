**Who wrote it:** Acme DevRel (devrel-tools), vendored at 0.4.1 on 2026-10-05 and not reviewed by our team before this week; on the wire it calls itself `package-registry 1.30.0`, which is the MCP SDK version, so nothing in the handshake proves which build we run. Only our vendored copy, pinned in our repo, does.
**What it can reach:** it is a stdio subprocess running as our OS user, so MCP gives it no sandbox: it can read any file we can (`~/.ssh`, this repo's `.env` with API keys) and open any outbound connection (`urllib` to whatever `REGISTRY_URL` says). Our host passes it only PATH/HOME/USER-style env plus its two config vars, but that does not stop it reading disk. Its tool descriptions and `instructions` are pasted into our model's prompt, and its tool list changes with any publish.
**What it logs:** every tools/call is appended with timestamp, tool, arguments (package and version asked for), `$USER` and upstream. The default path is `~/.cache/package-registry-mcp/access.log`, outside the repo and never rotated; we redirected it to `week9/logs/registry_access.log`. It does not log the token, but in upstream mode DevRel's API sees every query too.
**What a stolen token could do:** `REGISTRY_TOKEN` is a bearer token, and DevRel issues publish-scoped tokens by default. A thief could publish or yank `acme-sdk` releases and rewrite deprecation notices, poisoning both customers' `pip install` and our agent's answers. With a read-only token, they could only read registry metadata (low impact). Today we run snapshot mode with no token set.
**Ship or don't:** ship, but only in snapshot mode or with a read-only token: pinned by sha256 in `week9/vendor/`, behind `week9_gateway.py` (per-tool scopes plus one audit line per call), and re-reviewed on every version bump. Don't ship it with a publish-scoped token or as an auto-updating dependency.
